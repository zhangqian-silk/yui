### 整体判断

- **机制明确、值得保留**：同请求去除无关/重复输出，当前状态与历史分开，
  必要完整原文可取回，已知独立读取可成组，准确回执减少纯传输核验读回，
  消除无意义通知。成立范围通常是接口/局部路径，不自动覆盖整个会话。
- **收益未稳定**：更深的 Skill 拆分、批量/复用指导、摘要线索、Role整包文案。
  多个能力已实现，但使用率、补读与模型往返决定全链效果。
- **仍需找中间点**：核心/手册粒度，默认返回/按需全文，完整目录/窄导航，
  冷读批量/暖轮增量，完整短回执/大正文指针。按完成一个动作的总成本选，
  不按最短入口或某一轮最低token选。
- 不要求每条 Agent 轨迹必降，也不把小样本写成“绝大多数场景已证明”。
  低风险机制可按工程价值保留；广泛收益需要代表性运行分布支持。

## 3. 成本口径：为什么少正文也可能多累计输入

必须分开记录：

| 指标 | 含义与限制 |
| --- | --- |
| 静态UTF-8字节 | 文件/响应的体积；不能直接当token，文件变短也不等于任务少读。 |
| 实际可见新增内容 | 本轮工具响应、指令、用户输入等；记录完整/截断边界，隐藏的文件捕获不是模型看过。 |
| 原文重复下界 | 同一来源、revision/digest和正文区间再次可见的量；分同轮/跨轮/恢复后合理重建。未识别部分是unknown，不是0。 |
| 模型请求累计input | 各请求input之和，通常包括该请求携带的历史。必须核对Provider字段语义、去重和时间范围。不是“正文去重后的token”。 |
| cached input／output | 缓存通常是input的子集，不能再加进input；input减cached只作拆分指标，不等于账单或推理成本。缺失字段保持缺失。 |
| 模型往返／工具／CLI | 独立response回执、native工具调用、真实CLI进程是不同计数。一条shell可执行多个CLI，工具次数不能冒充模型请求数。 |
| 延迟、完成量、失败 | 按等量业务成果看成本；同时报告失败/中断/重试及未完成阶段，提前停链不算优化。 |

概念上，累计输入为 `Σ request.input`。某次较早读取的文本若持续留在后续
请求上下文，会多次计入input；这是历史携带，不代表工具反复返回了同一页。
分页本身只控制新输出，不能保证Provider每次只接收该页。反过来，工具反复
读取同一digest/区间才是可直接证明的重复取回。两者应分别归因。

使用明确的response/Turn身份去重。若终态为Thread累计usage，不能把每轮终态
再次相加；只有范围连续、字段语义相同、未重置时才可作差。计数下降、基线缺失、
更新不一一对应均须暴露。缺少完整请求组装时不能精确分摊每段正文贡献，
不能从工具输出字节倒推出隐藏系统提示、工具定义或最终费用。

### 上下文压缩前后的行为与成本

历史报告中的“第四轮”只是特定实验的轮次定位，不代表所有第四轮都有问题，
也不证明该轮发生过压缩。后续重点按实际上下文压缩事件及其前后行为组织分析，
不按固定轮号设置问题窗口或性能门槛。

1. **定位边界与证据**：记录可观测的compaction事件及其Thread/Turn/时间或请求
   位置，区分同Thread压缩、新Thread、Session恢复和普通业务变更。未观测不等于
   未发生；只有上下文缺失迹象时标记为待确认，不能凭input骤降或cached变化断言压缩。
2. **压缩前的积累**：展开边界前的逐请求input、新增输出、重复原文和额外往返，
   分清必要业务材料与无效积累。是否影响压缩触发时机需要独立证据，不能只凭文本变多推断。
3. **压缩后的重建**：检查首次动作及随后稳定阶段保留了哪些任务事实、授权约束、
   当前版本和来源指针；是否按实际缺失重读必要Skill及原文，还是重新发现全部历史。
   压缩摘要不能代替必须完整读取的来源；也不能假设所有可用原文都已丢失。
4. **质量与效果边界**：检查是否遗漏更正、混用旧版本、重复提交或重放已完成效果。
   用持久事实与准确回执恢复处理状态，不靠压缩摘要推定已处理或未处理。
5. **比较完整代价**：分别报告压缩前积累、压缩过程可观测开销、压缩后重建及稳定
   运行的成本与完成量。不同轨迹按实际事件边界和等量业务对齐，而非强行对齐第四轮；
   没有压缩事件的窗口另列。压缩后单次input下降不等于全窗口净收益。
6. **保留归因限制**：边界附近若同时升级、恢复或改变任务，单列混杂因素；缺少
   Provider请求组装或压缩内容时不补造原因。同时分析各Role与全链，避免把另一
   Role的额外发现、修复或普通波动直接归因于压缩或候选。

## 4. 以后如何直接复盘线上实际轨迹

### 先选范围和身份，再取内容

以已授权的实际 Operator/Leader 会话为来源，默认只读既有数据。
记录时间窗、业务类型/完成量、产品构建、CLI入口、Skill版本/可恢复hash、
模型与配置、Role/Session/Thread/Turn关系、升级和恢复边界。新会话运行当前
安装不证明老会话曾加载同一文件；没有历史正文就不拿当前正文补作历史证据。

先用现有当前上下文/结果目录定位必要的消息、结果和执行身份，再取准确原文和
已有原生轨迹。不要扫描全部Home、所有用户会话或私有推理；避免导出凭据、
业务敏感原文和无关人员信息。分析副本保留内部映射、来源hash及缺失标记，
公开报告脱敏；不改业务DB、原件、旧评分或既有seal，不执行捕获的命令。

采样在看结果前说明：固定时间窗或连续合格任务，覆盖常见冷启动、普通暖轮、
多次变更、长会话、可观测压缩前后和实际恢复；没有压缩的窗口另列，
不以固定轮号替代压缩事件。保留失败、未使用新能力及反向样本。
不只挑“明显省token”的会话，也不要求遍历历史全部主题。

### 先统计，再由 Agent 读实际轨迹解释

为每个动作窗口保留一行：

`来源定位 | 产品/Skill身份 | Role/Thread/Turn | 业务与完成量 | 冷/暖/恢复 |
机制是否有机会使用/实际使用 | input/cached/output | 响应/工具/CLI计数 |
可见输出及重复下界 | 错误/重试 | 原文与质量证据 | 覆盖缺口`

统计由工程完成；Agent针对显著增长、反向样本、机制未触发和质量问题，
读取实际命令、输出、消息及最终业务结果，给出解释：

- **确认事实**：例如context原文完整却又show、仅新请求变化却读回全部历史。
- **有证据的机制解释**：省掉一个发现步骤、增加一次必要补读、恢复重建的开销。
- **待验证假设**：入口诱导、语义不明确、Provider组装变化等，不写成模型内心原因。
- **建议**：保留／调整／撤回／继续观察，明确适用动作、风险和下一条能改变决定的证据。

### 没有线上A/B时怎样判断

真实轨迹先用于发现重复和判断机制是否生效，不伪装随机实验。
按业务类型、Role、完成量、会话长度、模型/配置和版本分层；升级前后若任务
难度、请求规模或故障率变化，不能直接将总量差归因于代码。

报告样本数、覆盖范围、每例差异、中位数/分布、成功率和失败成本；既看每任务
成本也看总成本，避免大任务支配合计或小任务支配均值。足够独立任务时才讨论
不确定区间；同Thread的多轮相关，不能当作大量独立样本。先解释可见机制，
不要事后给候选臂额外操作统一贴“模型噪声”，也不要用单个异常否定整个方向。

对同一份数据离线重放**纯展示函数**，可验证字节/完整性变化；它不能证明Agent
会选择同样的操作。线上稳定有益、风险低的机械减负无需为每几KB再做模型实验。
只有无法从实际轨迹回答、且会改变采用决定的问题才汇总相关改动开展有界对照。
整体组合有益不证明每个组件有益；仅在拆分会影响采用时做定向消融。

## 5. 当前框架能做什么、还不能做什么

- `npm run eval:context:analyze -- <sealed-invocation> [paired-invocation]` 读取已有框架
  封存，输出归属明确的角色/阶段统计和检查。没有冻结源码时正文分类与重复量
  不测，不拿现工作区补齐。`history.mjs index/analyze` 可处理其支持的历史
  封存及准确源码归档；具体参数见脚本usage与README。
- `quantify.mjs`、`native-ownership.mjs`、`saved-evidence.mjs` 已有计量、
  去重、原生归属和证据完整性逻辑；CLI进程回执目前来自评测fixture wrapper，
  **不是线上默认埋点**。线上缺少它时不能把shell单词数填成真实CLI计数。
- **当前没有通用“任意线上会话目录→标准评测封存”的采集入口。** 上述命令不能
  直接当线上采集器，也不能给线上记录伪造plan/preflight/seal让校验通过。
  现阶段可在授权只读导出上按本指南做独立统计与Agent分析。若后续需要自动化，
  在现有归属/计量函数上增加薄的显式来源适配，保留native-only、missing、
  unsupported等覆盖状态；不建立第二套计数或伪造实验业务标准答案。
- 已有受限的[历史成本工具](../../../scripts/context-cost/README.md)，可以读取
  明确授权、准确选定的Codex rollout根会话及续接片段，统计原生usage、
  可见正文和压缩相关记录。它不执行Subject/review、不生成实验seal，
  不含所有子执行成本；rollout与app-server来源、去重键和窗口口径必须分开解释。
- 固定Skill hash义务映射只覆盖明确审阅的树；线上新版本不匹配时应局部标记
  无法自动判断，再读实际当时规则。不能一概阻止成本分析，也不能自动判遵循。
- 不完整工具输出、异步归属、Provider隐藏请求/组装/压缩、严格引用歧义、
  线上缺历史Skill正文仍是证据限制。语义正确性由Agent核对原件；
  导入失败不等于业务失败，导入成功不等于语义通过。
- 新实验的`agent-analysis`退出语义为采集/清理完成，不是质量通过。
  原失败和unknown保留；身份、权限、未知效果、handling与恢复安全边界仍独立。
  token自动硬上限暂不在本次范围；不因此自动扩大实验或审查。

## 6. 下次接手的最短流程

1. 重新核对实际已合入/部署版本与本地候选差异，更新本页版本栏。
2. 优先选择一段已授权线上连续运行记录，保存只读来源及覆盖说明。
3. 按第3、4节统计，Agent检查高成本与反向轨迹，区分正文、往返、历史和故障。
4. 按方向更新结论：机制证实范围、尚未找到的粒度、质量风险、是否值得改。
5. 组合高价值改动，先确定性验证；必要时才新实验。不重复逐版微调→全链A/B→
   四轮审查的循环，不以消除全部unknown为目标。

每次复盘保留：日期/版本、来源与选样、覆盖缺口、指标表、代表性原文定位、
机制分析、质量与可靠性、采用建议及下一问题。新分析另存，不覆盖历史结论。
不把本文或历史所有报告加入每次Subject的常驻上下文。
