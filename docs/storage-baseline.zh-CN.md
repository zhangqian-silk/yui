# 存储基线 1.0

当前存储为 1.4。已声明的 1.3 → 1.4 迁移为正式项目知识增加适用信息和精确版本历史，
并将提案指纹扩展到适用范围、失效条件及替代意图。仅从精确匹配的已接受提案恢复
`scope`/`expiresWhen`；存量知识以已观察到的当前内容建立版本 1，不臆造缺失的修改历史。
已有提案的身份、审批和来源保留，冻结的 Context 快照及摘要不改写。物理 SQL 结构不变。

既有 1.2 → 1.3 迁移为结构化输入增加可选的精确 Session 限定和无 Assignment
时的明确未投递原因；既有按 Role 寻址的输入保持原样，不推断历史 Session 选择。

Yui 1.0.0 从唯一、纯净的持久化契约开始。软件包版本、存储结构、记录封装和
Controller 协议是相互独立的身份，不能从其中一个推断另一个。

## 当前契约

- `storage_schema` 记录权威的存储**主版本.小版本**和精确物理结构校验和。
- 新 Home 直接创建完整的当前 DDL。普通读取只接受当前身份，不规范化记录。
- 默认 `upgrade` 和 `update` 只能沿同一主版本内完整、已声明的小版本路径执行；
  初始 1.0 基线没有迁移步骤。
- 跨主版本、降级、未知或未声明的身份会在激活前被拒绝，并保持 Home 不变。
- 当前 Yui 自有封装和协议分别从版本 1 开始。业务 ID、revision、epoch、事件计数、
  Context 摘要和外部 Provider 协议相互独立，不随存储编号重置。
- `storage_migration_archive` 只保存当前已声明迁移的不透明审计证据，不是读取器、
  调度器或修复机制。
- 运行包和当前源码只包含当前契约及同主版本内已声明的小版本迁移机制。

未来持久化变更必须增加明确的存储小版本、源和目标校验和、确定性的事务转换，
并提供聚焦的回归证据。已经发布的基线不可改写。

## 失败与恢复

更新预检会在激活前校验暂存包和目标 Home，并在维护锁内再次检查。迁移失败会
回滚事务，不推进存储身份。

无效、损坏或不受支持的状态会被保留并给出诊断。Yui 不猜测修复、不丢弃证据，
也不会在其上静默初始化。Agent、Leader 或 Operator 可以检查精确失败，并选择
有界操作，例如重试、废弃受影响的执行、恢复已验证备份，或初始化独立的新 Home。

执行已授权的持久化更新前，应在 Controller 停止或由维护锁隔离时制作可恢复的
Home 备份。数据库及其匹配的 WAL/SHM 必须作为一个整体恢复，不能混用不同观察
时刻的文件。

真实 Home 操作、发布和共享基础设施验证需要用户明确授权；开发与 CI 使用隔离的
一次性样本。

## 发布产物边界

发布的运行 tarball 是唯一可执行发布产物，必须排除仓库测试、开发工具和非当前
存储材料。每个 GitHub Release 都携带 npm 发布所使用的同一份已测试运行包、
校验和与来源记录。
